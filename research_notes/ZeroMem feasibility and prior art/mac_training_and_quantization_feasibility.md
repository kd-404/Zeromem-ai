# Mac (M2 Pro, 8GB) Feasibility: From-Scratch Training + Local RAG Quantization

Context note: this research is for a solo developer building a portfolio/research project (ZeroMem), not a production deployment. All time/memory figures below are estimates unless a source is directly cited, and are flagged as such.

## PART A: Training a 20-50M parameter decoder-only transformer from scratch on M2 Pro / 8GB via PyTorch MPS

### Q1: Realistic dataset size / token budget for a ~30M parameter model to produce fluent, coherent text (TinyStories as reference)

#### Takeaway
The TinyStories paper (Eldan & Li, arXiv:2305.07759) is the direct precedent: it trained decoder-only GPT-Neo-style models from below 1M up to ~80M parameters on its ~470–480M-token synthetic dataset of simple children's stories, and found that models with well under 10M parameters (with at least 2 transformer layers) could already produce fluent, grammatically correct, multi-paragraph text; a ~30M-parameter model sits comfortably inside the paper's tested range and should be more than sufficient in capacity, provided it sees a similarly restricted-vocabulary, high-repetition dataset. The full ~470-480M-token TinyStories dataset (or a meaningful fraction of it, likely 100-300M tokens for a couple of epochs) is a reasonable token budget for a 30M model on this narrow-domain task — this is a much smaller token count than general-purpose LLM pretraining because the TinyStories domain is intentionally simplified (vocabulary limited to what a 3-4 year old understands).

#### Cited Findings
- TinyStories is "a synthetic dataset of short stories that only contain words that a typical 3 to 4-year-olds usually understand," generated by GPT-3.5 and GPT-4 — [TinyStories abstract via EmergentMind](https://www.emergentmind.com/papers/2305.07759)
- The dataset consists of approximately 480M tokens — [EmergentMind summary of TinyStories](https://www.emergentmind.com/papers/2305.07759)
- Models "with under 10M parameters" can produce coherent text when trained on TinyStories — [EmergentMind summary of TinyStories](https://www.emergentmind.com/papers/2305.07759)
- The paper tested a range of model sizes including 1M, 2.5M, 8.3M, 21M, 28M, and 33M parameters (varying 1-8 transformer layers), with embedding dimension 256, context length 512, and a reduced vocabulary of ~10,000 tokens (using the GPT-Neo tokenizer) — [arXiv:2305.07759 HTML](https://arxiv.org/html/2305.07759)
- "Training of generative models on TinyStories can typically be done in less than a day on a single GPU" — [arXiv:2305.07759 HTML](https://arxiv.org/html/2305.07759)
- Models below 10M total parameters can "produce fluent and consistent stories with several paragraphs," grammar mastery is achieved even by relatively small models, while consistency/creativity emerge at larger sizes, and instruction-following requires at least 2 transformer layers (single-layer models "struggle quite substantially") — [arXiv:2305.07759 HTML](https://arxiv.org/html/2305.07759)
- Small Language Models (SLMs) with fewer than 50M parameters can achieve noteworthy performance when trained on carefully constructed but much smaller (curated, low-diversity) datasets — [Regional Tiny Stories paper, arXiv:2504.07989](https://arxiv.org/pdf/2504.07989)

#### Inferences
- A ~30M parameter model is at or above the capacity the TinyStories paper found sufficient for fluent, grammatical, multi-paragraph text in this narrow domain — capacity is not the bottleneck; data quality/repetition and quality of the restricted vocabulary matter more.
- Because TinyStories intentionally limits vocabulary and complexity, the effective "tokens needed per parameter" ratio is far below general-purpose LLM scaling laws (e.g., Chinchilla's ~20 tokens/parameter would suggest only ~600M tokens for a 30M model, which is roughly in line with the ~470-480M token TinyStories corpus — but the actual sufficiency comes from domain narrowness, not from hitting a generic scaling-law target).
- For a solo developer replicating this on a single TinyStories-scale dataset, one to a few epochs over the ~470-480M token corpus (i.e., a token budget in the several-hundred-million to ~1B token range) is a reasonable, well-precedented target — not tens of billions of tokens as would be needed for a general-purpose model of similar size.

#### Gaps
- No source found gives an exact token count in the original paper's text; the ~470-480M-token figure is corroborated by secondary summaries only (EmergentMind), not the primary PDF's methods text directly — the primary PDF/HTML fetch returned architecture details but not an explicit dataset token count.
- No source specifies the exact number of training epochs Eldan & Li used over the dataset, so the precise total token budget consumed during training (dataset size x epochs) for their best small models is not confirmed.

### Q2: Realistic wall-clock training time for a ~30M parameter model on M2 Pro (10-core GPU) via PyTorch MPS, for one epoch over a few hundred million tokens

#### Takeaway
Direct, size-matched benchmarks (30M params, hundreds of millions of tokens, M2 Pro, MPS) were not found; the best available proxy is a nanoGPT run on an M2 MacBook (Simon Willison's TIL) with a much smaller model (3.42M params) and much smaller dataset (Shakespeare, ~1M characters) showing MPS ~135-244ms/iteration vs CPU ~414-553ms/iteration (roughly 2-3x speedup from MPS), which is consistent with general M2 PyTorch/MPS benchmarks. Scaling this proxy up by ~9x in parameters and by roughly 500x in token count (to reach "a few hundred million tokens" for one epoch) suggests a full epoch for a 30M-parameter model on M2 Pro would very plausibly take multiple hours to potentially a day or more of wall-clock time — this is an extrapolated estimate, not a directly sourced number, and should be treated as rough.

#### Cited Findings
- Using nanoGPT's `--device=mps` flag can "significantly accelerate training (2-3X)" versus CPU on Apple Silicon, allowing use of larger networks — [karpathy/nanoGPT GitHub](https://github.com/karpathy/nanogpt) (via search synthesis)
- On an M2 MacBook Pro running nanoGPT on the Shakespeare dataset with a 3.42M-parameter model (4 layers, 4 heads, 64 embedding dim, 39MB checkpoint): the MPS run completed 6,184 iterations in ~3.5 minutes (~135-244ms/iteration), while the CPU run took ~11 hours for 142,862 iterations (~414-553ms/iteration) — [Simon Willison's TIL: Running nanoGPT on M2](https://til.simonwillison.net/llms/nanogpt-shakespeare-m2)
- In MNIST training benchmarks, CPU execution took 141.26 seconds, about 2.5x longer than the GPU (MPS) version — [oldcai.com PyTorch M2 MNIST benchmark](https://www.oldcai.com/ai/pytorch-train-MNIST-with-gpu-on-mac/) (via search synthesis)
- Some users have reported occasional stability issues with the MPS backend in certain training configurations — [search synthesis of nanoGPT MPS discussions, incl. karpathy/nanoGPT issue #217](https://github.com/karpathy/nanoGPT/issues/217)

#### Inferences
- The Willison benchmark model (3.42M params, tiny dataset) is roughly 9x smaller than a 30M-parameter target, and its dataset (~1M characters, likely under 1M tokens) is orders of magnitude smaller than "a few hundred million tokens." Naively scaling compute by parameter count and token count together (compute for a transformer roughly scales as ~6 x params x tokens per the general LLM training-compute heuristic) implies several thousand times more compute than the Willison run — even with the reported MPS iteration times of ~150-250ms for a much smaller model/batch, one epoch of a 30M model over hundreds of millions of tokens on an M2 Pro is very likely to require multiple hours at minimum, and plausibly a full day or more, depending heavily on batch size, sequence length, and how much gradient accumulation is needed to fit in 8GB (see Q4).
- No directly-sourced wall-clock number for a 30M/hundreds-of-millions-of-tokens run on M2 Pro MPS was found; any single number quoted for this scenario should be presented as a rough order-of-magnitude estimate (low single-digit hours to roughly a day for one epoch), not a benchmark-backed figure.

#### Gaps
- No benchmark or forum post was found that trains a model in the 20-50M parameter range on M2 Pro MPS specifically, nor one using a TinyStories-scale token count. This is a genuine gap; estimates above are extrapolations from a much smaller proxy benchmark, not direct citations.
- No data found on M2 Pro's specific 10-core GPU variant vs. other M2 Pro GPU core counts (M2 Pro ships with 16- or 19-core GPU configurations in Apple's actual lineup; the "10-core GPU" figure in the prompt may reflect a base M2, not M2 Pro — flag this discrepancy to the report writer since it affects which benchmarks are comparable).

### Q3: Known pitfalls/gotchas of PyTorch MPS backend for training (as of 2025-2026)

#### Takeaway
As of 2025-2026, PyTorch's MPS backend remains behind CUDA in operator coverage and has several documented rough edges for training specifically: missing/unimplemented ops for certain layers (e.g., some normalization backward kernels), historical silent-failure bugs in in-place ops, and multiple open GitHub issues describing memory-reporting inaccuracies and leaks — all of which matter for a from-scratch training run of any duration.

#### Cited Findings
- MPS backend lacks support for many operations; there is a centralized PyTorch tracking issue for MPS operator coverage — [MPS operator coverage tracking issue #141287](https://github.com/pytorch/pytorch/issues/141287); also see the older tracking issue [#77754](https://github.com/pytorch/pytorch/issues/77754)
- As of libtorch 2.9, some operations (e.g., `aten::native_group_norm_backward`) have no MPS kernel, which can cause training failures for models using certain normalization layers — [pytorch/pytorch MPS backend wiki and related issues, synthesized from search](https://github.com/pytorch/pytorch/wiki/MPS-Backend)
- A historical PyTorch MPS kernel bug caused `addcmul_` and `addcdiv_` to silently fail when writing to non-contiguous output tensors, freezing model encoder weights during training on Apple Silicon (affected PyTorch versions before 2.4) — [search synthesis; see "the bug that taught me more about PyTorch than years of using it"](https://elanapearl.github.io/blog/2025/the-bug-that-taught-me-pytorch/)
- Setting `PYTORCH_ENABLE_MPS_FALLBACK=1` allows PyTorch to fall back to CPU for operations not yet implemented on MPS, at a performance cost — [search synthesis of PyTorch MPS docs](https://docs.pytorch.org/docs/2.13/notes/mps.html)
- `torch.mps.driver_allocated_memory()` returns total GPU memory allocated by the Metal driver, including cached MPSAllocator pool allocations — but there are multiple open issues describing memory growth not reflected by `torch.mps.current_allocated_memory()` / `driver_allocated_memory()` even though Activity Monitor shows it, and specific leak reports (e.g., `torch.unique` in a loop causing unrestricted driver-memory growth; an SDPA float32 memory leak; a leak when using `.to()` for simultaneous device+dtype conversion) — [torch.mps.driver_allocated_memory docs](https://docs.pytorch.org/docs/stable/generated/torch.mps.driver_allocated_memory.html); [MPS memory leak issue #164299](https://github.com/pytorch/pytorch/issues/164299); [torch.unique leak issue #145151](https://github.com/pytorch/pytorch/issues/145151); [SDPA float32 leak issue #152344](https://github.com/pytorch/pytorch/issues/152344); [.to() leak issue #114096](https://github.com/pytorch/pytorch/issues/114096); [general MPS memory leak issue #154329](https://github.com/pytorch/pytorch/issues/154329)
- There are reports of an "MPS backend out of memory" error that can be resolved by manually emptying the MPS cache, suggesting the allocator does not always reclaim memory proactively — [pytorch/pytorch issue #105839](https://github.com/pytorch/pytorch/issues/105839)
- Some users have reported occasional stability/NaN issues training with MPS in nanoGPT-style setups — [karpathy/nanoGPT issue #217, "Nan's training with 'MPS'"](https://github.com/pytorch/nanoGPT/issues/217)

#### Inferences
- For a multi-hour or multi-day training run (as Q2 suggests may be needed), memory-leak-prone long-running MPS processes are a real operational risk on an 8GB machine: even a slow leak in driver-allocated memory could eventually force an OOM or require manual process restarts / cache-clearing / checkpoint-resume workflows.
- Mixed-precision training support on MPS is less mature/more restricted than CUDA's (e.g., historical bf16/fp16 gaps and the encoder-freezing `addcmul_`/`addcdiv_` bug specifically affected optimizer-adjacent in-place ops), so a from-scratch training script should be tested carefully for correctness (e.g., verify loss actually decreases, don't assume mixed precision "just works" as smoothly as on CUDA) and may need to stick to fp32 or bf16 with fallback rather than aggressive fp16 AMP.
- Given known missing ops for some normalization backward passes, an architecture choice using widely-supported ops (standard LayerNorm rather than more exotic normalization) reduces the risk of hitting an unimplemented MPS kernel.

#### Gaps
- No source directly benchmarks MPS training speed relative to a comparable CUDA GPU for a nanoGPT-scale model in 2025/2026 (the "2-3x slower than CPU... 2-3x faster than CPU" framing found is CPU-vs-MPS, not MPS-vs-CUDA); the widely-repeated general claim that "MPS is slower than CUDA" is plausible but no controlled recent benchmark was found and cited here.
- No source confirms whether the specific memory leaks (e.g., `torch.unique`, SDPA float32) are fixed in the exact PyTorch version a developer would use in September 2026; these should be treated as known risk areas to test for, not confirmed current-version bugs.

### Q4: Is 8GB unified memory sufficient for this training run (model + optimizer states + activations + data batches)?

#### Takeaway
No source was found that directly measures peak memory for a ~30M-parameter transformer training run on 8GB unified memory, but standard training-memory arithmetic combined with sourced facts about macOS memory pressure and Apple Silicon's shared CPU/GPU memory pool indicates that 8GB is workable but tight: the model + Adam optimizer states alone are well under 1GB, but activation memory (which scales with batch size x sequence length x hidden dim x layers) plus the OS, Python/PyTorch runtime, and any concurrently open apps can plausibly push a naive full-batch configuration into memory pressure, likely forcing small per-step batch sizes and/or gradient accumulation to stay stable — a well-established mitigation pattern in memory-constrained Apple Silicon deployments generally.

#### Cited Findings
- Apple Silicon uses unified memory shared between CPU and GPU; macOS reports memory pressure at three levels (normal, warn, critical), and when pressure reaches "warn," loading additional memory-consuming work will likely cause swapping — [search synthesis, "MLX prefix cache" issue and related discussion](https://github.com/ollama/ollama/issues/18131)
- If system-wide memory pressure reaches "critical," a model or workload is "spilling into swap, and generation speed will collapse"; the typical fix cited for LLM inference under this condition is a lower quantization level or shorter context — [search synthesis, InsiderLLM Mac M-series guide](https://insiderllm.com/guides/running-llms-mac-m-series/)
- (From Part B/C research) 7B-tier or higher models "induce persistent memory swap thrashing on 8GB machines," which is part of why 3B-tier models are recommended as the practical ceiling for 8GB Macs — [search synthesis, ModelPiper Ollama multi-model guide](https://modelpiper.com/blog/ollama-multi-model-mac)

#### Inferences
- Rough back-of-envelope memory math for a 30M-parameter model in fp32: weights ≈ 120MB, Adam optimizer states (2x fp32 momentum buffers) ≈ 240MB, gradients ≈ 120MB — under 500MB total for model+optimizer, which by itself easily fits in 8GB.
- The dominant, harder-to-predict memory cost is activations: for a transformer, activation memory scales roughly linearly with batch_size x sequence_length x num_layers x hidden_dim (times a small constant for attention/MLP intermediates). At TinyStories-like settings (context length 512, embedding dim ~256-384 typical for this parameter range), activation memory should be modest per-sample, meaning moderate batch sizes (e.g., 32-64) are plausible on 8GB, but this has not been benchmarked here and should be validated empirically by the developer with `torch.mps` memory calls once flagged as unreliable (see Q3) — i.e., watch Activity Monitor, not just `torch.mps.current_allocated_memory()`.
- Given (a) unified memory is shared with the OS and any other running apps, (b) MPS memory reporting is known to be unreliable (Q3), and (c) macOS aggressively swaps once pressure hits "warn," a cautious approach — small batch size with gradient accumulation to reach an effective larger batch, plus closing other memory-heavy apps during training — is the realistic path to a stable run on 8GB, rather than assuming large batches will simply work.

#### Gaps
- No source gives measured peak memory (GB) for a real ~20-50M parameter transformer training run under PyTorch MPS. This is an estimate derived from general training-memory arithmetic and general Apple Silicon memory-pressure behavior, not a directly cited benchmark — flagged clearly here as an inference, not a fact.
- No source specifies exact batch size / gradient accumulation settings that worked for a comparable model+hardware combination.

## PART B: Quantizing Qwen2.5-3B-Instruct from FP16 to Q4 using mlx-lm

### Q1: Is mlx-lm's quantization workflow straightforward for a solo developer? What's the typical command/process?

#### Takeaway
Yes — mlx-lm's quantization workflow is a single CLI command (`mlx_lm.convert`), documented by both Qwen's own MLX guide and the mlx-lm GitHub repo, and is widely used by the `mlx-community` on Hugging Face to publish pre-quantized models; this is one of the more turnkey quantization workflows available for Apple Silicon.

#### Cited Findings
- Basic quantization command: `mlx_lm.convert --hf-path Qwen/Qwen2.5-7B-Instruct --mlx-path mlx/Qwen2.5-7B-Instruct/ -q`, where `--hf-path` is the Hugging Face model name or local path, `--mlx-path` is the output directory, and `-q` enables quantization — [Qwen's MLX-LM documentation](https://qwen.readthedocs.io/en/latest/run_locally/mlx-lm.html)
- For explicit 4-bit quantization: `python -m mlx_lm.convert --hf-path [model-path] --mlx-path ./[output-path] --quantize --q-bits 4` — [search synthesis of mlx-lm usage examples](https://github.com/ml-explore/mlx-lm)
- A complete Qwen2.5 example: `mlx_lm.convert --hf-path Qwen/Qwen2.5-7B-Instruct --mlx-path ./mlx/Qwen2.5-7B-Instruct-4bit -q --q-bits 4` — [search synthesis, ml-explore/mlx-lm GitHub](https://github.com/ml-explore/mlx-lm)
- The `mlx-community` organization on Hugging Face publishes many pre-quantized 4-bit MLX models (e.g., `mlx-community/Qwen2.5-3B-Instruct-4bit`, `mlx-community/Qwen2.5-Coder-3B-Instruct-4bit`), indicating this conversion process is standard/repeatable enough to be done at scale by the community — [mlx-community/Qwen2.5-3B-Instruct-4bit on Hugging Face](https://huggingface.co/mlx-community/Qwen2.5-3B-Instruct-4bit); [mlx-community/Qwen2.5-Coder-3B-Instruct-4bit](https://huggingface.co/mlx-community/Qwen2.5-Coder-3B-Instruct-4bit)

#### Inferences
- Since `mlx-community/Qwen2.5-3B-Instruct-4bit` already exists as a pre-converted model on Hugging Face, a solo developer building ZeroMem doesn't necessarily need to run the conversion at all — they can download the pre-quantized model directly, which is even simpler than running `mlx_lm.convert` themselves. Running the conversion locally is still simple (one CLI command) if a custom quantization (e.g., different `--q-bits` or group size) is desired.

#### Gaps
- No source was found detailing typical conversion run-time or peak memory required for the conversion step itself (as opposed to running the resulting quantized model) on an 8GB machine — this could matter if the developer wants to do the quantization locally rather than downloading a pre-quantized model.

### Q2: Expected disk size and runtime memory footprint of Qwen2.5-3B at Q4 quantization via MLX

#### Takeaway
The MLX 4-bit quantized Qwen2.5-3B-Instruct model is approximately 1.74GB on disk, versus roughly 6.8GB for the native FP16 weights — a reduction of roughly 4x, consistent with 4-bit vs 16-bit weight storage; runtime memory footprint should be similar to or modestly above the on-disk size (activations, KV cache, and framework overhead add on top of static weight size).

#### Cited Findings
- `mlx-community/Qwen2.5-3B-Instruct-4bit` total model size is 1.74GB, for a 3B-parameter model, quantized to 4-bit, using U32/F16 tensor types — [mlx-community/Qwen2.5-3B-Instruct-4bit on Hugging Face](https://huggingface.co/mlx-community/Qwen2.5-3B-Instruct-4bit)
- Qwen2.5-3B-Instruct native FP16 weights total approximately 6.8GB (split across two files of ~3.98GB and ~2.82GB) — [search synthesis of Hugging Face Qwen2.5-3B-Instruct-GGUF/native file listings](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct)

#### Inferences
- 1.74GB (Q4) vs ~6.8GB (FP16) is roughly a 3.9x reduction, which lines up with the expected ~4x reduction from going from 16-bit to 4-bit weights (with a small overhead from quantization scale/zero-point metadata).
- Runtime RAM usage for inference will be somewhat higher than the 1.74GB on-disk figure once you add: the MLX/Python process overhead, tokenizer, KV cache for the active context (grows with sequence length and batch), and any other loaded state. A reasonable estimate (not directly sourced) for the Q4 model's actual RAM footprint during single-request inference is roughly 2-2.5GB, though this figure is an inference, not a citation.

#### Gaps
- No source gives a directly measured, in-context runtime peak RSS/GPU-memory figure for `mlx-community/Qwen2.5-3B-Instruct-4bit` while generating (as opposed to just the static file size on disk). The 2-2.5GB estimate above is inferred/rough and should be flagged as such to the report writer.

### Q3: Expected quality degradation at Q4 vs FP16 for Qwen2.5-3B specifically

#### Takeaway
No perplexity table specific to `Qwen2.5-3B-Instruct` at 4-bit vs FP16 quantization was found, but closely related evidence (Qwen2.5 family quantization studies covering 0.5B-32B, and a study explicitly measuring "Qwen-2.5 3B" under multiple 4-bit methods) indicates 4-bit quantization is generally well-tolerated by Qwen2.5-scale models, with perplexity increases in roughly the 5-15% range versus higher precision, and with smaller models showing somewhat more pronounced degradation than larger ones — consistent with general findings that 4-bit is a "safe" quantization level while going below ~3-bit is where things get risky.

#### Cited Findings
- For the Qwen2.5 family (0.5B, 7B, 14B, 32B) on WikiText-2, AWQ (a 4-bit method) achieves perplexities of 14.17, 7.00, 5.54, and 5.15 respectively (with a newer method, AAAC, achieving slightly better 13.66, 6.93, 5.45, 5.09) — [search synthesis citing AAAC paper results table](https://arxiv.org/pdf/2605.08692) (note: exact source paper URL for this specific comparison table was not independently re-verified beyond the search summary)
- For "Qwen-2.5 3B" specifically, under 4-bit quantization methods NF4, AF4, and BOF4, perplexity on WikiText-2 ranges from 12.05 to 13.48 — [search synthesis, referencing BOF4 paper arXiv:2505.06653](https://arxiv.org/pdf/2505.06653)
- As LLMs are quantized to 4 and 3 bits, perplexity increases slightly; INT4 shows "more noticeable degradation, with perplexity increases of 5-15% compared to FP32" — [search synthesis of quantization degradation literature](https://arxiv.org/html/2608.08188v1)
- "4-bit quantization typically retains performance, while 2-bit quantization often causes broad performance degradation. At 3-bit, the degradation becomes evident but highly variable... depending strongly on model scale, quantization method, and task type" — [search synthesis of quantization literature](https://arxiv.org/pdf/2402.16775)
- "Larger models exhibit greater robustness, while smaller models experience more pronounced degradation at low bit-widths... below about 3 bits, degradation becomes sharp, especially for small models" — [search synthesis, ParetoQ paper](https://www.arxiv.org/pdf/2502.02631v1)
- Aider-style coding benchmarks across quantization levels of Qwen2.5-Coder on Apple MLX found that "quantization does not matter" much for practical task performance in that specific evaluation — [Ivan Fioravanti, "Qwen 2.5 Coder: quantization does not matter — Aider benchmarks on Apple MLX"](https://medium.com/@ivanfioravanti/qwen-2-5-coder-quantization-does-not-matter-aider-benchmarks-on-apple-mlx-671e6bd5252a)

#### Inferences
- Taken together, the evidence suggests Q4 (4-bit) for Qwen2.5-3B-Instruct should preserve most practical quality for RAG-style tasks (retrieval-grounded generation, summarization, Q&A) — the same conclusion the community has reached in practice (hence the popularity of MLX 4-bit community conversions). Perplexity degradation is real (roughly 5-15% relative, per general quantization literature) but not the "broad degradation" seen at 2-bit.
- As a 3B model, Qwen2.5-3B is on the smaller end where degradation is somewhat more pronounced than a 7B/14B/32B sibling — worth keeping in mind if RAG answer quality seems noticeably worse than the FP16 reference during development.

#### Gaps
- No source was found benchmarking `Qwen2.5-3B-Instruct` (specifically, MLX's exact 4-bit quantization scheme, not GPTQ/AWQ/NF4 academic variants) head-to-head against its own FP16 baseline on a standard benchmark (perplexity or task accuracy). The cited numbers are from related but not identical quantization methods (NF4/AF4/BOF4/AWQ from academic papers) rather than MLX's specific group-wise quantization implementation — this is a meaningful gap since MLX may use a different scheme (e.g., group size, asymmetric quantization) than the academic methods cited.
- No direct comparison of MLX's own 4-bit quantization quality vs. GGUF Q4_K_M or GPTQ/AWQ was found in this pass.

### Q4: Is Q4 the right choice for an 8GB Mac, given concurrent embeddings model, reranker, and ZeroMem model?

#### Takeaway
Given the sourced evidence that 7B+ models cause persistent swap thrashing on 8GB Macs while 3B-tier models are the recommended practical ceiling, and that Qwen2.5-3B at Q4 is only ~1.74GB on disk (likely ~2-2.5GB at runtime, per Part B Q2's inference), Q4 is a reasonable and likely necessary choice for an 8GB machine — going to FP16 (~6.8GB) would leave little to no headroom for anything else, while dropping to Q3/Q2 would save comparatively little additional memory (see arithmetic below) while risking the sharper quality degradation the literature associates with sub-4-bit quantization, especially for smaller (3B) models. See Part C for the combined-footprint arithmetic across all concurrent components.

#### Cited Findings
- "An 8GB M1 Mac can run lightweight 1B to 3B models such as SmolLM2-1.7B, Phi-4-mini, and Llama 3.2 3B at 60 to 100 tokens per second for focused, single-turn tasks... Llama 3.2 3B (2GB) or Phi-4-mini (2.5GB) runs comfortably with headroom for macOS on 8GB machines" — [search synthesis, InsiderLLM Mac M-series guide](https://insiderllm.com/guides/running-llms-mac-m-series/)
- "For 8GB systems, models at the 7B tier or higher induce persistent memory swap thrashing on 8GB machines, which is why 3B models are recommended for this memory tier" — [search synthesis, ModelPiper Ollama multi-model guide](https://modelpiper.com/blog/ollama-multi-model-mac)
- "Below about 3 bits, degradation becomes sharp, especially for small models" — [search synthesis, ParetoQ paper](https://www.arxiv.org/pdf/2502.02631v1)

#### Inferences
- Since a Q4 3B model (~2GB class) is explicitly cited as running "comfortably with headroom" on 8GB Macs for single-model use, and the developer needs headroom for several additional concurrent components (see Part C), Q4 — not Q3/Q2 — is the right default: going lower in bit-width saves only a fraction of a GB more (quantization savings shrink as you go from 4→3→2 bits, since going 16→4 is already a 4x reduction, while 4→3 is only another ~25% reduction) while introducing materially more quality risk per the cited literature. A smaller base model (e.g., Qwen2.5-1.5B) at Q4 would free up more memory margin than moving Qwen2.5-3B to Q3/Q2, if headroom turns out to be insufficient in practice (see Part C).

#### Gaps
- No source directly quantifies Q3 or Q2 file sizes for Qwen2.5-3B via MLX specifically, so the exact GB savings of going from Q4 to Q3/Q2 for this model could not be confirmed numerically — the "shrinking returns" inference above is based on general knowledge of quantization arithmetic, not a cited number for this specific model.

## PART C: Full local RAG pipeline concurrently on 8GB unified memory

### Q1: Is bge-small-en + cross-encoder reranker + Qwen2.5-3B-Q4 + ZeroMem (~30M) + FastAPI + ChromaDB realistic within an 8GB budget?

#### Takeaway
Based on sourced component sizes, the models themselves are individually small and their combined static memory footprint (roughly 2.5-3GB, per the estimates below) should fit within 8GB with some margin — but the sourced material also warns that macOS memory pressure and swap behavior (not raw file sizes) is the actual failure mode on 8GB machines, and ChromaDB's in-memory HNSW index and general OS/Python/FastAPI overhead are the parts most likely to erode the margin; this is very likely realistic for the low-scale, single-user "portfolio project" use case described, but headroom will be tight rather than generous, especially if ChromaDB's index grows or if request concurrency increases.

#### Cited Findings — Component-by-component (with rough memory estimates)
- **Qwen2.5-3B-Instruct at MLX Q4**: 1.74GB on disk — [mlx-community/Qwen2.5-3B-Instruct-4bit](https://huggingface.co/mlx-community/Qwen2.5-3B-Instruct-4bit). Estimated runtime footprint (inference, per Part B Q2 inference): roughly 2-2.5GB (not directly sourced, includes KV cache/overhead — flagged as estimate).
- **bge-small-en-v1.5** (embedding model): 33.36M parameters (12 layers, 384 hidden dim); ~63.63MB at fp16/bf16, or ~15.91MB at int4; ~0.1GB VRAM at BF16, effectively ~0.0GB (rounds down) at INT4 — [PromptLayer / HF automated model memory requirements discussion for BAAI/bge-small-en-v1.5](https://huggingface.co/BAAI/bge-small-en-v1.5/discussions/10). Realistic estimate for this component in a Python process: well under 0.5GB including framework overhead.
- **Cross-encoder reranker (cross-encoder/ms-marco-MiniLM-L-6-v2)**: 23M parameters, BERT-based — [search synthesis, cross-encoder/ms-marco-MiniLM-L6-v2 on Hugging Face](https://huggingface.co/cross-encoder/ms-marco-MiniLM-L6-v2). At fp32 this is roughly 90MB of weights (23M x 4 bytes); realistic estimate for this component including framework overhead: well under 0.5GB.
- **ZeroMem custom model (~30M params)**: at fp32, weights alone ≈ 120MB (per Part A Q4 arithmetic); at fp16 ≈ 60MB. Inference-only memory (no optimizer states needed post-training) should be well under 0.5GB including overhead — this is an inference/estimate, not directly sourced.
- **ChromaDB**: "The minimum realistic footprint for a production RAG stack with ChromaDB, LangChain, and FastAPI is 8GB RAM and 4 vCPUs" (production-scale framing, not solo/local-only) — [search synthesis, Fastio ChromaDB storage guide](https://fast.io/resources/ai-agent-chroma-storage/). "Chroma's HNSW index memory footprint scales roughly with vector count and graph connectivity (M, ef_construction), not linearly with disk size — collections that look small on disk can still exhaust RAM at query time" — [search synthesis, same source]. For a single-node, low-tens-of-millions-of-vectors workload, Chroma+LangChain+FastAPI is described as workable on a 16GB host in production framing; for a solo dev's much smaller (likely thousands to low-hundred-thousands of vectors) local knowledge base, footprint should be much smaller than these production figures — [search synthesis, same source]
- **FastAPI + Python runtime overhead**: no specific figure was sourced; general Python/FastAPI process overhead is typically in the tens to low hundreds of MB range for a simple app (not independently cited here — general knowledge, flagged as an estimate).

#### Inferences
- Rough combined static/model-weight memory estimate: Qwen2.5-3B-Q4 (~2-2.5GB) + bge-small-en (~0.2-0.3GB) + cross-encoder reranker (~0.2-0.3GB) + ZeroMem (~0.1-0.2GB) + ChromaDB index (likely well under 0.5GB for a small solo-scale corpus) + FastAPI/Python/macOS overhead (roughly 1-2GB is typical for macOS + a Python process with several ML frameworks loaded, per general Apple Silicon memory-pressure behavior cited in Part A) totals very roughly 4-6GB. This leaves some margin under 8GB but not a large one, especially once real usage (concurrent requests, larger contexts, multiple chat turns accumulating KV cache) is considered.
- The most likely failure mode, per the sourced material on macOS memory pressure (Part A Q4) and ChromaDB's HNSW RAM scaling (this section), is not any single component being individually too large, but cumulative pressure pushing macOS into "warn"/"critical" memory states, triggering swap and degraded performance — this is consistent with the sourced general guidance that on 8GB Macs, 3B-tier (not 7B+) is the practical LLM ceiling, and that quantization / shorter context is the standard mitigation once pressure is observed.
- For a solo developer's portfolio/research project (not concurrent multi-user production traffic), this combination is very likely realistic to run and demo, provided: (a) Qwen2.5-3B stays at Q4 (per Part B Q4), (b) the ChromaDB corpus stays modest (thousands to tens of thousands of chunks, not millions), (c) context lengths are kept reasonable, and (d) the developer monitors macOS memory pressure/Activity Monitor directly rather than trusting framework-reported memory stats alone (per Part A Q3's finding that MPS/framework memory reporting can be unreliable).

#### Gaps
- No source directly measured the combined, concurrent memory footprint of this exact 5-component stack (embedder + reranker + quantized 3B LLM + custom small model + ChromaDB + FastAPI) on an 8GB Mac. All combined-footprint figures above are derived by summing individually-sourced or estimated component sizes, not from an end-to-end measurement — this should be clearly flagged to the report writer as the single biggest uncertainty in Part C, and ideally validated empirically (e.g., via Activity Monitor) once the developer has an implementation to test.
- No source quantifies typical FastAPI/Python process baseline memory or ChromaDB's actual RAM use at a small (solo-project) vector count; the production-scale ChromaDB figures found (8GB minimum, up to 10-20M vectors) are not representative of a much smaller personal knowledge base and were noted as such above, but a small-scale-specific figure was not found.
